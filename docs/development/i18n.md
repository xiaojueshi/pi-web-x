# UI internationalization

[Documentation index](../README.md) · [Documentation conventions](./documentation.md)

Pi Web X uses a small internal i18n layer for client-visible interface text. It does not translate API contracts, user content, Agent/model output, commands, paths, provider names, or server error details.

## Built-in locales

| Locale id | Language |
| --- | --- |
| `en` | English |
| `zh-CN` | Simplified Chinese |
| `zh-TW` | Traditional Chinese |

The initial locale is selected from browser preferences. Traditional Chinese regions and `zh-Hant` variants resolve to `zh-TW`; bare `zh`, Simplified Chinese regions, and `zh-Hans` variants resolve to `zh-CN`. Users can change the locale in the top bar.

The language choice is persisted in the existing shared `pi-locale` localStorage key. It is not a legacy `pi-web:*` product preference; do not introduce or read legacy `pi-web:*` keys.

## Using translations

Components rendered below `I18nProvider` obtain the translation function from `useI18n`:

```tsx
import { useI18n } from "@/hooks/useI18n";

export function ExampleButton() {
  const { t } = useI18n();
  return <button aria-label={t("example.open")}>{t("example.open")}</button>;
}
```

`src/client/main.tsx` installs the provider at the client root. Do not create another provider for individual features.

Use parameters rather than concatenating translated fragments:

```tsx
<span>{t("session.messageCount", { count: messageCount })}</span>
```

```ts
"session.messageCount": "{count} messages"
```

This lets every locale control word order and punctuation.

## Adding or changing UI text

1. Choose a stable, language-neutral key under a feature namespace such as `chat.*`, `files.*`, `settings.*`, or `common.*`.
2. Add the key to every built-in package in `lib/i18n/messages/`.
3. Translate visible text, `title`, `aria-label`, and `placeholder` values.
4. Use interpolation for counts, names, paths, and other runtime values.
5. Keep product names, model/provider names, commands, paths, and user/Agent content unchanged.
6. Do not translate an API error by matching its English text; translate only the local fallback around it.
7. Extend registry/format tests when locale matching, parameters, or fallback behavior changes.

Established technical terms may remain in English when that makes the UI map clearly to commands or configuration: `Agent`, `API Key`, `Provider`, `Token`, `worktree`, `Diff`, `CWD`, `Shell`, `Git`, `HEAD`, `OAuth`, and `Mermaid`. Preserve conventional casing.

Example:

```ts
// en.ts
"files.uploadedCount": "{count} uploaded"

// zh-CN.ts
"files.uploadedCount": "已上传 {count} 个文件"

// zh-TW.ts
"files.uploadedCount": "已上傳 {count} 個檔案"
```

The formatter falls back to English and finally to the key itself. Tests require built-in locale packages to have the complete English key set and compatible interpolation placeholders, so incomplete packages fail validation instead of silently drifting.

## Adding a locale

### 1. Create the package

Add `lib/i18n/messages/<locale>.ts` with a BCP 47-style id:

```ts
import type { LocalePlugin } from "../types";

/** Pi Web X Japanese language package. */
export const jaLocale: LocalePlugin = {
  id: "ja",
  label: "日本語",
  messages: {
    "common.language": "言語",
  },
};
```

Start from the complete English key set and provide the same placeholder names.

### 2. Register it

Import the package in `lib/i18n/registry.ts` and add it to the built-in locale list. Update the `Locale` union and locale detection rules in `lib/i18n/types.ts`/registry code where the built-in ids are intentionally enumerated.

### 3. Test it

Update:

- `tests/unit/lib/i18n/registry.test.ts` for registration, browser-language resolution, key parity, and placeholder parity;
- `tests/unit/lib/i18n/format.test.ts` for interpolation, fallback, and locale-aware formatting.

Run:

```bash
bun test tests/unit/lib/i18n
bun run typecheck
bun run lint
```

## README translations versus UI locales

The root `README.*.md` translations are project documentation and are not generated from UI locale packages. Their language set may differ. README translation policy is defined in [documentation conventions](./documentation.md); UI locale behavior is defined here.

## Design principles

Internationalization is an accessibility and usability feature. Contributions may improve one coherent group of messages, but every built-in package must remain structurally complete. The i18n layer stays inside the client so translations cannot alter API behavior, pi data, or model output.
